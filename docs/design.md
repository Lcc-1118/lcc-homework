# 设计说明

## 背景

远川物流在「仓内拣选与装车核验」投入大量人力。核心痛点（来自 FDE 需求发现报告 `docs/fde/00-项目证据与需求发现报告.md`）：

1. 取消订单已进波次、拣完仍被装车、到站才发现（`f11`、`f44`）；
2. 相似包装 SKU 相邻货位，新员工常拿错规格（`f10`、`f14`）；
3. 错发率/漏扫口径不定，验收无法签字（`f42`、`f53`）；
4. 数据口径与接口治理，故障期需人工兜底（`f30`~`f35`）。

## 设计目标

做一个**可运行的协同助手 CLI**，在合成样本上走通「波次 → 拣选 → 复核 → 装车」的完整核验，产出：取消拦截、错配提醒、交接清单、审计留痕、口径核算，并在不可逆动作前转人工。

## 关键设计决策

### 1. 取消拦截不放行（REQ-1）

- 检出波次中已取消订单 → `action=block` + `human_review=True`；
- 即使检出，也**转人工**（波次计划员核对，`f15`、`f44`），不自动移除/不自动放行；
- 取消事件同步延迟 12 分钟（`f31`），故拦截结果标记「暂未更新」由人工兜底。

### 2. 错配提醒不越界（REQ-2）

- 只做「扫码解释 + 错配提醒」，`auto_operate=False`（不操作叉车/盘盈盘亏，`f52`）；
- 显示原记录与待确认字段（`f15`）。

### 3. 歧义进人工修复队列（REQ-5）

- 主编号/版本/事件时间缺失 → `ValidationIssue` 进 `repair_queue`，不进自动推荐样本（`f33`）。

### 4. 漏扫为零是硬门槛（REQ-3）

- `missing_scans == 0` 才 `miss_scan_zero=True`；
- 口径（分母/排除规则/周期/出数人）未书面固定前，`confirmed=False`，验收不可签字（`f42`、`f53`）。

### 5. 审计可重建（REQ-4）

- 每条建议记录：`req`、`business_no`、`version`、`fact_refs`、`result`、`human_edit`、`signer`、`ts`；
- 可按业务编号重建处理链（`f45`）；不记录账号口令或个人敏感信息。

## 边界（不做什么）

- 不自动操作叉车、不做盘盈盘亏（`f05`、`f52`）；
- 不写入业务系统、不自动批准（`f32`、`f41`）；
- 波次计划员不代替安全主管完成专业签核（`f22`）；
- 取消单/缺依据/版本冲突/系统不可用 → 转人工（`f44`）。

## 已知局限

- 合成业务场景，真实接口、真实样本（取消单占比/错配单量/到站收货）未核实；
- 口径、审批矩阵、放行责任待业务确认；
- 数据更新频率为每天两次（`f34`），非实时。
